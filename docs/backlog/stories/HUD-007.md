## Context

Epic: `EPIC-03`. This story builds three components from
`docs/wiki/design/components.md`:

- **C-26, the lobby panel.** It shows who is here, whether there are enough, and
  the countdown, which holds below `players_min`. There is no ready toggle.
- **C-05, the seat card.** At round start it shows your helper and your partner
  with hue rings, eye and key glyphs, and two sample machines.
- **C-04, the relations strip.** It keeps the seat card on screen all round, so
  nothing about who helps whom has to be remembered (`loop.md` §1a).

The player-facing words come from `voice.md`. The seat data is the private
`SeatView` (`SLICE-003`). The lobby data is the public `RoundView.players`.

**Which required gate would fail if this story's artifact broke:** `unit`. The
look is `D-1`, checked in Studio.

## Design notes

Lead Designer rulings on the glyph gaps AC-4 (PT-A7, PT-T3) exposes. Every key
below already exists in `tokens.md` §2.4; no new token. Field names (`glyph`,
`struck`, `overlay`) are additions to the `## Contract` output shapes, for the
Lead PO to fold in.

- **DN-1** — `LobbyModel.describe` returns a top-level `glyph`, one per state and
  pairwise distinct: `waiting` -> `glyph.wait` (clock with no hands: held),
  `counting` -> `glyph.notyet` (hourglass: time running), `full` -> `glyph.done`
  (all here). No turn result exists in `Lobby`, so reusing these keys collides
  with nothing on screen.
- **DN-2** — Slots carry no glyph field. A slot is not a panel state: empty vs
  filled is `playerId == nil` vs set, needed vs optional is `needed`, drawn as a
  solid vs dashed `stroke.control` border (shape, not colour, not words). A
  filled slot's identity is the headshot, or the hue circle on loading/error.
- **DN-3** — The only output field that may hold a `color.player.*` token is
  `hueToken` (slot ring, chip ring, swatch, sample trim). No model returns a text
  colour; names are drawn in `color.text.primary` by the view. Test: walk every
  output table; any `color.player.*` value appears only under the key `hueToken`.
- **DN-4** — "You" (C-04 `you`, C-05 `you`) carries `glyph = nil`, and the test
  asserts it is nil (not merely skips it). PT-A7 does not apply: it requires a
  glyph per *state* so a state change reads without words, and `you` has exactly
  one state (`present`; the viewer cannot see their own screen while away).
  "Which one is me" is carried by position (centre of helper -> you -> partner)
  and, on C-05, by size (large). `glyph.key`/`glyph.eye` would be wrong here:
  you are both someone's helper and someone's partner.
- **DN-5** — C-04 helper `none`: `glyph = "glyph.eye"`, `struck = true`,
  `playerId = nil`, `hueToken = nil` (the dashed circle is `stroke.control`, no
  hue). Every other chip state has `struck = false`. The slash is drawn by the
  view, as `glyph.dark` draws its slash; it is not a separate key.
- **DN-6** — C-04 partner `none`: `partner = nil` (chip hidden, strip shrinks).
  Nothing is shown, so there is no state to carry a glyph.
- **DN-7** — C-04 `away`: `glyph` keeps the relation glyph (helper `glyph.eye`,
  partner `glyph.key`) and `overlay = "glyph.wait"`; `overlay = nil` in every
  other state. The relation glyph must survive (A-9: who helps whom stays on
  screen). The 50% opacity is the view's, derived from `state == "away"`.
- **DN-8** — C-04 `loading`/`error` and C-05 loading/error: same `glyph` as
  `present`, `struck = false`, `overlay = nil`; the state field alone
  distinguishes them (the view swaps headshot for hue circle).
- **DN-9** — C-05 samples, exactly two, in this order: yours = viewer's
  `hueToken` + `glyph.key`; partner's = `dependentId`'s `hueToken` +
  `glyph.eye`. Confirmed against `tokens.md` §1.3 (lens-class machines are
  trimmed in the partner's hue with the eye). Swapping either pairing must fail.

## Acceptance criteria

- **AC-1** — Given a `RoundView` in `Lobby`, when
  `LobbyModel.describe(view, players_min, players_max)` runs, then it returns
  `players_max` slots, of which the first `players_min` are `needed` and the
  rest `optional`. Filled slots appear in `players` order, and each has the
  hue token for its index. The state is `waiting` below `players_min`
  (countdown held), `counting` at or above it, and `full` at `players_max`.
- **AC-2** — Given a `SeatView`, when
  `SeatCardModel.describe(seatView)` runs, then:
  - the helper is `supplierId`, with `glyph.eye`;
  - the partner is `dependentId`, with `glyph.key`;
  - each person's hue is the token for their index in `seatOrder`;
  - the sample machines are trimmed in the viewer's hue (key) and the partner's
    hue (eye).

  *Control:* a model that swaps supplier and dependent must fail. That is the
  direction error `Ring.luau`'s header warns about.
- **AC-3** — Given a `SeatView` and a presence map, when
  `RelationsModel.describe` runs, then each chip's state is `present`,
  `loading`, `error`, `away` or `none` as the C-04 table specifies. After a
  helper has left, the helper chip is `none` with the struck eye.
- **AC-4** — Given any model output here, when it is inspected, then it contains
  no player hue on text (PT-T3's usage clause), and every state has a glyph or
  icon key (PT-A7).

## Contract

**Modules**, pure, under `src/client/models/`:

    LobbyModel.describe(view: RoundViewLike, playersMin: number, playersMax: number)
        -> { state: "waiting" | "counting" | "full", slots: { { playerId: string?, needed: boolean, hueToken: string? } } }
    SeatCardModel.describe(seat: SeatViewLike) -> { helper: Person, you: Person, partner: Person, samples: { Sample } }
    RelationsModel.describe(seat: SeatViewLike, presence: { [string]: "present" | "loading" | "error" | "away" })

**PO decisions (reported to the operator before RED, 2026-10-09).**
- **PO-1. "Your helper has left" is read against the DEALT seat view.** When a
  helper is withdrawn (after `disconnect_grace_seconds`, `Ring.withdraw`), the
  ring closes. The dependent's new `supplierId` is the leaver's own supplier,
  and that player's lens reads the class they inherited, not yours
  (`mechanics.md` §8: "the leaver's lens is lost"). So no single `SeatView`
  can say "no helper". The client keeps the first `SeatView` it receives after
  leaving `Lobby` (the *dealt* view) and passes it to `RelationsModel`:
  - helper is `none` iff `seat.supplierId ~= dealt.supplierId`;
  - partner is `none` (and `partner = nil`, DN-6) iff
    `seat.dependentId ~= dealt.dependentId`.

  A rejoin inside the grace window restores the dealt seat, so the rule
  reverses on its own. AC-3's text ("a SeatView and a presence map") is
  unchanged: the dealt view is a third input it did not name.
- **PO-2. Hues come from the DEALT `seatOrder`.** `Ring.withdraw` removes the
  leaver from `players`, so the current `seatOrder` shortens and every later
  index shifts. `tokens.md` §1.2 says a hue is stable from lobby into round.
  `RelationsModel` therefore takes hue indices from `dealt.seatOrder`.
  `SeatCardModel` runs at deal time, when the current view and the dealt view
  are the same, so it uses its own argument's `seatOrder`.

**Hue token.** For index `i` (1-based) the token is `` `color.player.{i}` ``,
for example `"color.player.3"`. A key existing in `Theme.color` is part of the
assertion. A `playerId` that does not appear in the `seatOrder` being indexed
raises, naming the id.

**Exact shapes.** All live under `src/client/models/`. All are pure and require
nothing but `../Theme` or `@game/ReplicatedStorage/Shared/…`. Every returned
table is fresh.

    LobbyModel.describe(view: { players: { string } }, playersMin: number, playersMax: number)
        -> { state: "waiting" | "counting" | "full", glyph: string,
             slots: { { playerId: string?, needed: boolean, hueToken: string? } } }
      -- #slots == playersMax; slots[i].needed == (i <= playersMin)
      -- slots[i].playerId == view.players[i] (nil past #players); hueToken nil iff playerId nil
      -- state: #players >= playersMax -> "full"; >= playersMin -> "counting"; else "waiting"
      -- glyph (DN-1): waiting "glyph.wait", counting "glyph.notyet", full "glyph.done"
      -- view.phase is not read. #players > playersMax is unspecified.

    export type Person = { playerId: string, hueToken: string, glyph: string? }
    export type Sample = { hueToken: string, glyph: string }
    SeatCardModel.describe(seat: SeatViewLike)
        -> { helper: Person, you: Person, partner: Person, samples: { Sample } }
      -- helper  = { seat.supplierId,  hue by seatOrder, "glyph.eye" }
      -- you     = { seat.playerId,    hue by seatOrder, glyph = nil }   (DN-4)
      -- partner = { seat.dependentId, hue by seatOrder, "glyph.key" }
      -- samples = { { you.hueToken, "glyph.key" }, { partner.hueToken, "glyph.eye" } }, exactly, in that order (DN-9)

    export type ChipState = "present" | "loading" | "error" | "away" | "none"
    export type Chip = { playerId: string?, hueToken: string?, glyph: string?,
                         state: ChipState, struck: boolean, overlay: string? }
    RelationsModel.describe(seat: SeatViewLike, presence: { [string]: "present" | "loading" | "error" | "away" },
                            dealt: SeatViewLike)
        -> { helper: Chip, you: Chip, partner: Chip? }
      -- helper none (PO-1, DN-5): { playerId nil, hueToken nil, glyph "glyph.eye", state "none", struck true, overlay nil }
      -- partner none (PO-1, DN-6): partner == nil
      -- otherwise helper/partner: playerId = seat.supplierId / seat.dependentId,
      --   hueToken by dealt.seatOrder (PO-2), glyph "glyph.eye" / "glyph.key",
      --   state = presence[id], or "loading" when the map has no entry, struck false,
      --   overlay "glyph.wait" iff state == "away" (DN-7), else nil (DN-8)
      -- you: { seat.playerId, hue by dealt.seatOrder, glyph nil, state "present", struck false, overlay nil }

    export type SeatViewLike = { playerId: string, keyClasses: { number }, lensClass: number,
                                 supplierId: string, dependentId: string, seatOrder: { string } }
      -- structural, declared in the client (in SeatCardModel, re-used by RelationsModel). Never required from src/server/.

**AC-4, mechanical (DN-3, DN-4).** One test walks every output of all three
models over every state the AC-1 to AC-3 tests build. It asserts:
- every string value matching `^color%.player%.` sits under a key named exactly
  `hueToken`;
- every `LobbyModel` output has a non-nil `glyph`;
- every non-nil `Chip` and every `Person` other than `you` has a non-nil
  `glyph`;
- `you.glyph` is nil in both C-05 and C-04;
- every glyph value is a member of `Theme.icons.system`.

The walk needs a negative control. It must report a model that puts a
`color.player.*` value under any other key, `textColour` for example. RED runs
that control in memory.

**Views (Studio-verified, D-1; `typecheck`, `lint` and `build` read them).**
- `src/client/views/LobbyPanelView.luau`: `mount(parent)` returns an object with
  `render(LobbyModel output)` and `hide()`. Needed slots get a solid
  `stroke.control` border and optional slots a dashed one. A filled slot shows
  the headshot in a `stroke.player` ring. Below `players_min` it shows
  `glyph.wait`, and "Waiting for friends" when 1 player is present.
- `src/client/views/SeatCardView.luau`: `mount(parent)` returns an object with
  `show(SeatCardModel output)` and `collapse()`. It collapses after
  `design.seat_card_seconds` (4 s), or on any tap, click, Esc, `ButtonB` or
  movement input. It never sinks input.
- `src/client/views/RelationsStripView.luau`: `mount(parent)` returns an object
  with `render(RelationsModel output)` and `hide()`. It is not a focus stop.
- Headshots come from `Players:GetUserThumbnailAsync` inside `pcall`, one per
  player id, cached. On failure the view shows the hue circle, never a broken
  image. The view reports each id's fetch state (`loading`, `present`, `error`)
  through a callback, so the glue can build `presence`.
- Words come from `Words.seat` and `Words.lobby`. Glyphs are drawn as Theme icon
  keys (a placeholder TextLabel per key is acceptable in M3; the key, not the
  art, is the decision).

**Client glue (`Main.client.luau`).**
- It listens to `ClientTransport.on("SeatView", ...)` as well as `RoundView`.
  It keeps `dealt`: the first `SeatView` after the phase leaves `Lobby`, reset
  on re-entering `Lobby`.
- The lobby panel shows in `Lobby` and hides otherwise.
- The seat card shows once per deal. The strip renders from `Round` onwards
  while a `SeatView` is held.
- Presence is the view's fetch state. It is overridden to `away` when no
  `Player` with that `UserId` is in `Players`. Player ids are
  `tostring(UserId)` (SLICE-004).
