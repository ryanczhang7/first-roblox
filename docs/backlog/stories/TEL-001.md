## Context

Brief **B6** says build telemetry in M2, not later, and **A5** says instrument the
three discovery buckets — D1, days 2–7, days 8–28 — **separately from day one**,
because Roblox's Recommended For You measures them separately and first-play
bounce is a direct ranking penalty.

This story builds the envelope and the sink interface. It emits nothing; `TEL-002`
and `TEL-003` add the emitters. Splitting it that way is deliberate: the envelope
is the thing every later emitter agrees on, and getting the bucket mapping wrong
is cheap now and expensive once nine call sites exist.

The architectural decision behind it (`architecture.md` §6, D3): **emission is an
effect, not a call.** Pure code returns `{ kind = "Emit", event }` and a driver
hands it to the sink. Three things follow: telemetry is verified with no sink at
all, a sink failure cannot break a round, and the events become part of the phase
machine's tested output rather than a side channel nobody asserts on.

**Which required gate would fail if this story's artifact broke:** `unit`.

## Acceptance criteria

- **AC-1** — Given a clock at `t`, when an event is constructed, then its `at`
  field is `t` — taken from the injected clock — and its `name`, `bucket`,
  `sessionId` and `fields` are the values supplied.
- **AC-2** — Given the bucket mapping, when it is read, then it names **all nine**
  B6 events with these buckets: `join` D1, `first_round_complete` D1,
  `bounce_before_resolution` D1, `session_end` D1, `round_complete` D2_7,
  `rematch_accepted` D2_7, `day_n_return` D8_28, `co_play_with_known_player`
  D8_28, `purchase` D8_28.
- **AC-3** — Given an event name not in the mapping, when an event is constructed
  with it, then construction fails rather than producing an event with a guessed or
  absent bucket.
  *Control:* an implementation that defaults an unknown name to D1 **must** fail
  this. A silent default is how a metric quietly starts measuring the wrong bucket.
- **AC-4** — Given a recording sink, when three events are emitted, then it holds
  exactly those three, in order, with their fields intact.
- **AC-5** — Given a sink whose `emit` raises, when an event is emitted through the
  dispatch helper, then the raise does not propagate to the caller, and the failure
  is itself recorded as a counted drop.
  *Control:* an implementation that lets the error propagate **must** fail this;
  one that swallows it with no count must fail the "counted" half. Telemetry that
  can crash a round is worse than no telemetry, and telemetry that silently drops
  is worse than either.
- **AC-6** — Given the `fields` table of an event, when a value is not a string,
  number or boolean, then construction fails naming the offending key.
  *Semantics:* `fields` is a flat map of scalars. A nested table is a payload
  nobody downstream can index, and a `PlayerId` that is an Instance is a memory
  leak and a replication hazard.

## Contract

### `src/shared/telemetry/Event.luau`

    export type Bucket = "D1" | "D2_7" | "D8_28"

    export type TelemetryEvent = {
        name:      string,
        at:        number,                       -- seconds, from the injected Clock
        bucket:    Bucket,
        sessionId: string,
        playerId:  string?,
        fields:    { [string]: string | number | boolean },
    }

    Event.BUCKETS : { [string]: Bucket }         -- frozen; all nine B6 names
    Event.new(name: string, at: number, sessionId: string,
              playerId: string?, fields: { ... }?) -> TelemetryEvent

`at` is passed in, never read. Nothing in this module calls a clock —
`ROUND-001`'s guard test would catch it, and that is the point of the guard.

### `src/shared/telemetry/Sink.luau`

    export type Sink = { emit: (TelemetryEvent) -> () }

    Sink.noop() -> Sink
    Sink.recording() -> RecordingSink            -- RecordingSink.events : {TelemetryEvent}
                                                 -- RecordingSink:clear()
    Sink.dispatch(sink: Sink, events: { TelemetryEvent }) -> DispatchResult
    -- DispatchResult = { delivered: number, dropped: number }

`Sink.dispatch` is where AC-5 lives: it isolates each `emit`, counts drops, and
never raises. It is the only function a driver calls.

### The three events declared and not emitted

`day_n_return`, `co_play_with_known_player` and `purchase` need persistence and are
M5. They are **in `BUCKETS` and have no emitter**, so M5 adds an emitter rather
than a vocabulary, and the gap is visible in the mapping rather than discovered
later. A test asserting "every name in `BUCKETS` has an emitter" would therefore be
wrong today; do not write one.

### `bounce_before_resolution` is the one to get right

A5 makes first-play bounce a direct ranking penalty, so it is the most valuable
event in the list and the easiest to emit twice or not at all. Its **rule** —
emitted when a player leaves while the phase is `Lobby`, `Assignment` or `Round`,
at most once per player per round, never during `Resolution` or `Post` — belongs to
`TEL-002`. This story only fixes its name and bucket.

## Model guidance

**Resolved model of every dispatch, by name:** _(record at dispatch.)_

AC-2 is **settled** and should be briefed as such: the nine events and three
buckets are the brief's, and a Test Developer invited to "design the event set"
will produce a better one that measures something A5 does not.

## Out of scope

- Any emitter. `TEL-002` (round lifecycle) and `TEL-003` (remote rejections).
- Any real sink. What telemetry goes to on a live server — an analytics service, a
  DataStore, Roblox's own AnalyticsService — is an M5 decision with request-budget
  and throttling consequences. Here, `noop` and `recording` are the only
  implementations, and that is sufficient because emission is an effect.
- Batching, sampling, back-pressure or retry. All belong with a real sink.
- Any client-side telemetry. There is no client.
- Personally identifying anything. `playerId` is a Roblox user id as a string and
  nothing else is carried.
