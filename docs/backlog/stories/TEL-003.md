## Context

The last story of M2, and the one that turns the trust boundary from a wall into
an instrument.

`NET-001`–`NET-003` reject malformed, out-of-phase and flooded calls and return a
`Rejection` naming which of the five checks fired. Nothing consumes it. A spike in
one rejection kind is the earliest signal an exploit attempt gives, and without
this story the server discards that signal at the moment it produces it.

B4's premise is that the clients are hostile and B1 #2 forbids shipping code that
does not pass the gates — neither says anything about *noticing*. This is the
noticing.

It is deliberately last in the epic because it depends on the whole pipeline
existing, and it is deliberately separate from `TEL-002` because the emission point
is different (the net wrapper, not the phase machine) and the exactly-once rule is
different.

**Which required gate would fail if this story's artifact broke:** `unit`.

## Acceptance criteria

- **AC-1** — Given a guarded remote and a call rejected for each of the five
  reasons in turn, when the wrapper returns, then exactly one telemetry event is
  produced per rejected call, carrying the remote name, the rejection reason and the
  sender's player id.
- **AC-2** — Given an **accepted** call, then no rejection event is produced.
  *Control:* an implementation emitting on every guarded call passes AC-1 and
  **must** fail this. Emitting on accepts would bury the signal under the traffic
  it is meant to stand out from — in a game where `signal_rate_limit_seconds` is
  1.5 and `players_max` is 6, accepted calls outnumber rejections by orders of
  magnitude in normal play.
- **AC-3** — Given a rejection, when its event is inspected, then the `reason`
  field holds exactly the `Rejection.reason` string — `identity`, `shape`, `range`,
  `phase` or `rate` — and not a collapsed or reworded value.
  *Semantics:* these five strings are the contract `NET-001` fixed and a later
  story may not reorder or rename them without an `## Amendments` entry, because
  this event is what makes historical exploit metrics comparable.
- **AC-4** — Given a rejection event, when its `fields` are inspected, then they
  contain no argument value from the rejected call.
  *Semantics:* the arguments are hostile input of unvalidated shape and unbounded
  size — that is why they were rejected. Copying them into telemetry gives an
  attacker a write primitive into the operator's own logs. The `detail` string from
  `Rejection` is developer-authored and safe; the payload is not.
  *Control:* an implementation that puts `rawArgs` in `fields` **must** fail this,
  and must also fail `TEL-001`'s scalar-fields check when the payload is a table —
  assert both, because one implementation could pass one of them.
- **AC-5** — Given a player flooding a remote at 100 calls per second across 10
  simulated seconds, when the events are counted, then the number of rejection
  events is bounded rather than equal to the number of rejections.
  *Semantics:* telemetry that scales one-to-one with a flood is an amplifier — the
  attack the limiter prevented arrives through the logging path instead. Emit at
  most one `rate` rejection event per player per remote per
  `rejection_report_interval_seconds`, with a count of suppressed rejections in
  `fields`.
  *Control:* the unbounded implementation produces 1,000 events; the bounded one
  must produce at most 11 over 10 seconds at a 1-second interval, with the
  suppressed count summing to 1,000. Assert the sum — a coalescer that drops the
  count is losing the measurement it exists to preserve.
- **AC-6** — Given rejections for two different players, when they are coalesced,
  then the coalescing is per player and per remote: one player's flood does not
  suppress another player's first rejection.

## Contract

### New constant

`rejection_report_interval_seconds` = **1**, and it is an engineering constant, not
a game-tuning one: it does not appear in `docs/wiki/game/tuning.md` and must not
be added there. It lives in the net layer's own configuration alongside the
`RateLimiter`, and its rationale is AC-5's — bound the amplification without losing
the count.

### Changes

*Amended at PLANNED → RED by the orchestrator (lead-po), before dispatch. The
original block gave `GuardContext` a bare `emit` field and the reporter a
`record(playerId, remoteName, reason, detail, now)`. Three defects, each found by
reading the tree rather than the plan: nothing supplied the `sessionId` that
`Event.new` requires; a reporter owned privately by each `guard()` closure could
never be flushed, so AC-5's trailing window would be unreportable; and `detail`
is **not** safe — see PO decision 2 below. RED may amend any block here in place
with a reason; GREEN builds what the amended block says.*

`src/net/Wrapper.luau` — `GuardContext` gains **one optional field**:

    telemetry: {
        reporter: RejectionReporter.RejectionReporter,
        emit: ({ TelemetryEvent }) -> (),
    }?

`nil` means nothing is recorded and nothing is emitted, exactly as today. When
present, every call `guard` **rejects** is passed to `reporter:record(...)`, and if
that returns an event, `emit({ event })` is called once, before the `Rejection` is
returned. An **accepted** call touches neither (AC-2). The reporter is the
driver's, shared across every remote it guards, and not built inside `guard`: the
driver is the one that holds a timer and calls `flush`. `emit` takes a batch, the
shape `Sink.dispatch` consumes; the driver is expected to pass
`function(batch) Sink.dispatch(sink, batch) end`, which is what keeps a raising
sink from erroring a server thread — the wrapper does not `pcall` `emit` itself.

**This is a signature change to an existing exported type.** Callers of
`GuardContext` grepped before dispatch (`rg "isSeated =" src tests`) — RED cannot
find these itself, since the old shape still type-checks during RED:

*Amended in RED by the test-developer, 2026-09-24 — the timestamp read.* The
reporter reads no clock and `record` takes `now`, so the wrapper supplies it, and
the only time source a `GuardContext` has is `context.clock`. NET-003's frozen
checks (`RateContract.clockIsReadOnlyByCallsThatReachTheRateCheck` and its AC-5)
pin **zero** clock reads on a call `identity`, `shape`, `range` or `phase`
rejected — for the contexts they build, none of which carries `telemetry`. So the
two promises are reconciled by the field: with `telemetry = nil` the wrapper
reads the clock exactly as today (never before check 5); with `telemetry`
present, a **rejected** call reads `context.clock.now()` to stamp the event, and
`at` is that value. The tests pin `at == context.clock.now()` at the moment of
the call against a manual clock and do **not** pin the read count, so reusing
the limiter's read for a `rate` rejection or reading again are both conforming.
An accepted call with `telemetry` present reads the clock no more than today.

*Also pinned in RED:* `emit` receives a table of exactly one event that is
`Deep.equal` to the one `record` returned — not identity, so a copy is
conforming. Nothing is emitted when `record` returns `nil`.

`src/net/RejectionReporter.luau` — new:

    RejectionReporter.INTERVAL_SECONDS = 1     -- rejection_report_interval_seconds
    RejectionReporter.new(intervalSeconds: number, sessionId: string) -> RejectionReporter
    reporter:record(playerId: any, remoteName: string, reason: Reason, now: number)
        -> TelemetryEvent?
    reporter:flush(now: number) -> { TelemetryEvent }

where `Reason` is `Wrapper.Rejection`'s five-string union, re-declared, not imported
(`Wrapper` requires this module; the reverse edge is a cycle, as for `RateLimiter`).
Nothing here reads a clock; `now` is always a parameter.

- **`identity`, `shape`, `range`, `phase` are never coalesced.** `record` returns
  an event for every one, with `count = 1` (AC-1: exactly one event per rejected
  call, for each of the five reasons).
- **`rate` is coalesced per `(playerId, remoteName)`** (AC-5, AC-6). A key has a
  window start `w` and a pending count `p`. On a `rate` rejection at `now`: if the
  key has no window, or `now - w >= intervalSeconds` (inclusive, as `RateLimiter`
  is), `record` returns an event with `count = 1 + p`, then sets `w = now`,
  `p = 0`; otherwise it sets `p += 1` and returns `nil`.
- **`flush(now)`** returns one event per key with `p > 0`, carrying `count = p`
  and `at = now`, and sets that key's `p = 0` (the window start is unchanged).
  Order is by `playerId`, then `remoteName`, ascending, so the result is
  deterministic. A flush with nothing pending returns `{}`.
- Consequence, and AC-5's control: 1,000 `rate` rejections from one player on one
  remote at `now = i / 100`, `i = 0..999` (computed, **not** accumulated —
  summing 0.01 drifts), then `flush(10)`, yields exactly **11** events — window
  openings at 0, 1, …, 9 carrying counts 1, 100, …, 100, and the flush carrying
  99 — whose `count`s sum to **1,000**. The unbounded control yields 1,000 events.

### The event

    name      = "remote_rejected"
    bucket    = "D1"
    at        = now
    sessionId = the reporter's
    playerId  = the caller id if it is a string, else nil
    fields    = { remote = remoteName, reason = reason, count = n }

and **nothing else** in `fields`. Specifically:

- **No `detail`** (PO decision 2). **No argument value, ever** (AC-4).
- A non-string caller id — an exploiter sending a table as the id, which the
  wrapper already survives for `identity` — is not put in the envelope, whose
  `playerId` is `string?`, and not put in `fields` either: `fields.caller` would
  be one more attacker-chosen value in the log. The event carries `playerId = nil`.

`remote_rejected` is **not** one of B6's nine events. It is an operational event,
not a retention one, and it needs adding to `Event.BUCKETS` — which `TEL-001`
AC-3 makes a deliberate act rather than something that can happen by accident. Add
it there, with a comment saying it is operational. D1 is chosen because exploit
attempts concentrate in first sessions; if that proves wrong it is a one-line
change with a story behind it.

**A TEL-001 test changes with it.** `TelemetryContract.bucketsNameExactlyTheNineB6Events`
(`tests/helpers/TelemetryContract.luau:263`) asserts `count == 9` and refuses any
extra key. `TEL-001` AC-2 says the mapping names *all nine*; it does not say it
names *nothing else*, so the test is stricter than its criterion and the criterion
needs no amendment. RED changes the helper to accept exactly the nine B6 events
**plus** an explicit operational set `{ remote_rejected = "D1" }`, and nothing
else — a stray eleventh key must still fail. That test is written against code
that does not yet have the entry, so it fails in RED for the right reason
(`remote_rejected` missing) and is earned by that failure; record it in the
handoff.

### PO decisions

1. **AC-5's count and flush** (put to the user at PLANNED → RED, 2026-09-24;
   answer: *count + flush*). As written, AC-5 asks for ≤ 11 events whose
   suppressed counts sum to 1,000, but under a `record`-only reporter the
   rejections coalesced after the last emitted event are never reported, so no
   implementation could reach the sum. The field is `count` — the rejections the
   event accounts for, itself included — and `flush(now)` reports trailing
   windows. The AC text is unchanged: "a count of suppressed rejections in
   `fields`" and "suppressed count summing to 1,000" are read as `sum(count)`.
   The flood control is driven **at the reporter**, where all 1,000 calls are
   rejections; through the wrapper some calls are accepted, so the wrapper-level
   flood asserts bounded events and `sum(count)` == the number of `rate`
   rejections the wrapper returned.
2. **`detail` stays out of the event.** AC-4's semantics note says the `detail`
   string is developer-authored and safe. It is not: `Schema.describe`
   (`src/net/Schema.luau:59`) echoes a number, a boolean, or a string of up to
   32 characters **verbatim** into `shape` and `range` details — `shape: expected
   a number, got "HOSTILE"` — and a hand-written schema that raises puts
   `tostring(err)` into the `shape` detail. Copying `detail` would break AC-4
   for exactly the reasons AC-4 gives. The criterion itself is unambiguous (no
   argument value in `fields`), so this is a contract decision, not an amendment;
   `record` therefore takes no `detail` parameter, which makes the leak
   unwritable rather than merely untested.
3. **Only `rate` is coalesced.** AC-5 names `rate`; AC-1 requires one event per
   rejected call for each reason. A flood of *malformed* calls is therefore
   still one event per call. That is the literal reading and it is the one built;
   bounding the other four is noted in `## Out of scope` as a follow-up.

## Out of scope

- Acting on the signal: banning, kicking, throttling harder, alerting. An operator
  activity informed by this data, decided in M6.
- Any dashboard or query layer.
- A real sink. `TEL-001` §Out of scope.
- Telemetry for the game's own mechanics — signals sent, actuations, instability.
  M3, and a different event family.
- Adding `rejection_report_interval_seconds` to `docs/wiki/game/tuning.md`. It is
  not a game constant and putting it there would invite it to be tuned for feel.
- The driver that calls `reporter:flush` on a timer and wires `emit` to
  `Sink.dispatch`. No driver exists for any remote yet.
- Coalescing `identity`, `shape`, `range` and `phase` floods (PO decision 3). A
  malformed-call flood is still one event per call; bounding it is a follow-up
  story, and AC-1 would need amending to allow it.

## Game design

This story implements no game mechanic. It is named here only to record one
boundary: `rejection_report_interval_seconds` is an **engineering** constant and
does not belong in `tuning.md`, whose §7 exists precisely so that the absence of a
constant reads as a decision.

One design fact does bear on it. `tuning.md` §3 gives
`signal_rate_limit_seconds` = 1.5 as serving two purposes — stream readability and
B4's rate-limit requirement — which means a `rate` rejection is not always an
attack. An honest player mashing the signal wheel produces them too. The event
carries the reason and the count and says nothing about intent; anyone reading it
should know that `rate` is the noisiest of the five and `identity` the quietest and
most alarming.
