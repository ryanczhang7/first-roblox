## Context

The last story of M2, and the one that turns the trust boundary from a wall into
an instrument.

`NET-001`–`NET-003` reject malformed, out-of-phase and flooded calls and return a
`Rejection` naming which of the five checks fired. Nothing consumes it. A spike in
one rejection kind is the earliest signal an exploit attempt gives, and without
this story the server discards that signal at the moment it produces it.

B4's premise is that the clients are hostile and B1 #2 forbids shipping code that
does not pass the gates — neither says anything about *noticing*. This is the
noticing.

It is deliberately last in the epic because it depends on the whole pipeline
existing, and it is deliberately separate from `TEL-002` because the emission point
is different (the net wrapper, not the phase machine) and the exactly-once rule is
different.

**Which required gate would fail if this story's artifact broke:** `unit`.

## Acceptance criteria

- **AC-1** — Given a guarded remote and a call rejected for each of the five
  reasons in turn, when the wrapper returns, then exactly one telemetry event is
  produced per rejected call, carrying the remote name, the rejection reason and the
  sender's player id.
- **AC-2** — Given an **accepted** call, then no rejection event is produced.
  *Control:* an implementation emitting on every guarded call passes AC-1 and
  **must** fail this. Emitting on accepts would bury the signal under the traffic
  it is meant to stand out from — in a game where `signal_rate_limit_seconds` is
  1.5 and `players_max` is 6, accepted calls outnumber rejections by orders of
  magnitude in normal play.
- **AC-3** — Given a rejection, when its event is inspected, then the `reason`
  field holds exactly the `Rejection.reason` string — `identity`, `shape`, `range`,
  `phase` or `rate` — and not a collapsed or reworded value.
  *Semantics:* these five strings are the contract `NET-001` fixed and a later
  story may not reorder or rename them without an `## Amendments` entry, because
  this event is what makes historical exploit metrics comparable.
- **AC-4** — Given a rejection event, when its `fields` are inspected, then they
  contain no argument value from the rejected call.
  *Semantics:* the arguments are hostile input of unvalidated shape and unbounded
  size — that is why they were rejected. Copying them into telemetry gives an
  attacker a write primitive into the operator's own logs. The `detail` string from
  `Rejection` is developer-authored and safe; the payload is not.
  *Control:* an implementation that puts `rawArgs` in `fields` **must** fail this,
  and must also fail `TEL-001`'s scalar-fields check when the payload is a table —
  assert both, because one implementation could pass one of them.
- **AC-5** — Given a player flooding a remote at 100 calls per second across 10
  simulated seconds, when the events are counted, then the number of rejection
  events is bounded rather than equal to the number of rejections.
  *Semantics:* telemetry that scales one-to-one with a flood is an amplifier — the
  attack the limiter prevented arrives through the logging path instead. Emit at
  most one `rate` rejection event per player per remote per
  `rejection_report_interval_seconds`, with a count of suppressed rejections in
  `fields`.
  *Control:* the unbounded implementation produces 1,000 events; the bounded one
  must produce at most 11 over 10 seconds at a 1-second interval, with the
  suppressed count summing to 1,000. Assert the sum — a coalescer that drops the
  count is losing the measurement it exists to preserve.
- **AC-6** — Given rejections for two different players, when they are coalesced,
  then the coalescing is per player and per remote: one player's flood does not
  suppress another player's first rejection.

## Contract

### New constant

`rejection_report_interval_seconds` = **1**, and it is an engineering constant, not
a game-tuning one: it does not appear in `docs/wiki/game/tuning.md` and must not
be added there. It lives in the net layer's own configuration alongside the
`RateLimiter`, and its rationale is AC-5's — bound the amplification without losing
the count.

### Changes

`src/net/Wrapper.luau` — `GuardContext` gains one field:

    emit: ({ TelemetryEvent }) -> ()      -- or nil, in which case nothing is emitted

**This is a signature change to an existing exported type.** Callers grepped before
dispatch — RED cannot find these itself, since the old shape still type-checks
during RED:

| Caller | File | What changes |
|---|---|---|
| `Wrapper.guard` | `src/net/Wrapper.luau` | reads the new field |
| NET-001 suite | `tests/net/wrapper_test.luau` | context construction helper |
| NET-002 suite | `tests/net/phase_legality_test.luau` | same |
| NET-003 suite | `tests/net/rate_limit_test.luau` | same |

Making `emit` optional keeps every existing test's context valid, which is why it
is optional rather than required. If RED finds a nil-check proliferating, amend
this block and make it required — but then all four call sites change together.

`src/net/RejectionReporter.luau` — new:

    RejectionReporter.new(intervalSeconds: number) -> RejectionReporter
    reporter:record(playerId, remoteName, reason, detail, now) -> TelemetryEvent?

Returns an event when one should be emitted, `nil` when the rejection was
coalesced into a pending window. `now` is passed in; nothing here reads a clock.

### The event

    name   = "remote_rejected"
    bucket = "D1"

`remote_rejected` is **not** one of B6's nine events. It is an operational event,
not a retention one, and it needs adding to `Event.BUCKETS` — which `TEL-001`
AC-3 makes a deliberate act rather than something that can happen by accident. Add
it there, with a comment saying it is operational. D1 is chosen because exploit
attempts concentrate in first sessions; if that proves wrong it is a one-line
change with a story behind it.

### Oracle partition

| AC | Kind | Instruction to RED |
|---|---|---|
| AC-1, AC-3 | **Settled** | The five reason strings are fixed in `NET-001`'s contract. Read them out; do not collapse, rename or reorder them. |
| AC-2, AC-4, AC-6 | **Mechanical, with controls** | AC-4's control has two halves and an implementation can pass one — assert both. |
| AC-5 | **Oracle-free** | You are designing the coalescing test. The numbers above (100 Hz, 10 s, ≤ 11 events, suppressed sum = 1,000) are the specified control; implement it literally, and if you believe a bound is wrong, say so before changing it — a widened bound here is a weakening. |

## Deferred verifications

None. The clock is injected and the flood is simulated.

## Model guidance

**Resolved model of every dispatch, by name:** _(record at dispatch.)_

Put AC-4's reasoning in the dispatch verbatim: **the rejected arguments are hostile
input and must not enter the log.** It is the least obvious criterion in the story
and the instinct of anyone writing diagnostics is to include the payload, because
that is what would be most useful if the input were trustworthy.

**Success condition:** AC-5's unbounded control is demonstrated producing 1,000
events against the bounded implementation's ≤ 11, with the suppressed counts
summing to 1,000 — measured, not described.

## Out of scope

- Acting on the signal: banning, kicking, throttling harder, alerting. An operator
  activity informed by this data, decided in M6.
- Any dashboard or query layer.
- A real sink. `TEL-001` §Out of scope.
- Telemetry for the game's own mechanics — signals sent, actuations, instability.
  M3, and a different event family.
- Adding `rejection_report_interval_seconds` to `docs/wiki/game/tuning.md`. It is
  not a game constant and putting it there would invite it to be tuned for feel.

## Game design

This story implements no game mechanic. It is named here only to record one
boundary: `rejection_report_interval_seconds` is an **engineering** constant and
does not belong in `tuning.md`, whose §7 exists precisely so that the absence of a
constant reads as a decision.

One design fact does bear on it. `tuning.md` §3 gives
`signal_rate_limit_seconds` = 1.5 as serving two purposes — stream readability and
B4's rate-limit requirement — which means a `rate` rejection is not always an
attack. An honest player mashing the signal wheel produces them too. The event
carries the reason and the count and says nothing about intent; anyone reading it
should know that `rate` is the noisiest of the five and `identity` the quietest and
most alarming.
