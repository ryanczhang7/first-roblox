## Context

Epic: `EPIC-04`. This story builds the Procedure as generated data
(`mechanics.md` §3.1–§3.2, §6.2; `tuning.md` §2 invariants):

- `procedure_length` steps, split into `procedure_tracks` = 2 tracks of
  `steps_per_track` = 4.
- Each class contributes exactly `stepsPerClass[c]` steps, as `GEN-002`
  placed them, so `INV_every_class_has_a_step` and `INV_balanced_steps` follow
  from the counts. Both are still asserted.
- Consecutive steps in a track are of different key classes
  (`INV_track_alternates`).
- The last step of each track is its half of the **finale**. The two finale
  machines are in different rooms at least `paired_room_distance_min` apart, of
  key classes **not adjacent on the ring** when n ≥ 4 (`INV_finale`). That
  makes the finale's two turners and two helpers four distinct players.
- `INV_k_essential` follows from the ring, `INV_every_class_has_a_step` and
  `dial_settings` ≥ 2, and is still tested directly per seed.

This is where the ring enters the generator (`architecture.md` D12).

**Which required gate would fail if this story's artifact broke:** `unit`.

## Acceptance criteria

- **AC-1** — Given n in `{4, 5, 6}`, a sweep of at least 1,000 seeds per n, and a
  ring from `Ring.assign`, when `Steps.draw` produces a candidate and `Steps.check`
  reports no violation, then the candidate has 2 tracks of `steps_per_track`
  distinct machines. Each class has exactly `stepsPerClass[c]` steps. Step counts
  per class differ by at most 1. No machine is a step twice.
- **AC-2** — Given the same accepted candidates, when each track is read in
  order, then no two consecutive steps share a key class
  (`INV_track_alternates`).
  *Control:* `check` must report a hand-built track `[c1, c1, c2, c3]`.
- **AC-3** — Given the same accepted candidates, when the finale is read, then
  its two machines are in different rooms with `Layout.distance ≥
  paired_room_distance_min`. When n ≥ 4, their key classes' holders are not
  ring neighbours, so neither is the other's supplier or dependent, and the set
  {turner 1, turner 2, helper 1, helper 2} has four distinct players
  (`INV_finale`).
  *Controls:* `check` must report finale machines in adjacent rooms, and
  finale classes held by ring neighbours.
- **AC-4** — Given the same accepted candidates, when any one player is removed
  from consideration, then at least one step has a machine that player alone can
  turn, and at least one step has a machine whose setting that player alone can
  read (`INV_k_essential`).
- **AC-5** — Given a candidate that violates an invariant, when `Steps.check`
  runs, then it returns one entry per violated invariant, each naming the
  invariant as `tuning.md` does (`INV_...`). An empty list means valid.
- **AC-6** — Given the sweep, when the fraction of first drawn candidates that
  pass `check` is measured per n, then it is at least 0.25 at every n, and the
  measured value is recorded in `## Notes` for `GEN-004`. The floor is the
  first-attempt acceptance `tuning.md: generator_attempts_max` is sized for, and
  the steps stage alone must clear it. It also keeps AC-1 to AC-4 and AC-7 from
  holding vacuously over an empty set (PO-2).
  *Control:* a `draw` that picks the two finale machines without regard to
  ring adjacency or room distance (otherwise correct) must fall below the floor
  at n = 4. At n = 4 only 2 of the 6 class pairs are non-adjacent, so roughly
  1/3 × P(distance ≥ 2) is expected. RED measures it and records it, and
  escalates if the measurement does not come out below the floor.
- **AC-7** — Given the accepted candidates of a sweep over seeds 1, 2, 3, …
  per n, continued until both pools hold at least 16,000 settings (and capped at
  20,000 seeds, failing if the cap is reached first), when required settings
  are pooled separately per n over step machines and over decoys (machines in
  the placement that are not steps), then in each pool each value's frequency
  lies within `1/dial_settings` ± 0.02 (`INV_settings_uniform`, "decoys
  included"). At 16,000 settings the standard error is about 0.0034, so ± 0.02
  is about 6σ (PO-3).
  *Control:* a `draw` that prefers machines whose `requiredSetting` is 1 when
  choosing steps must fail the step pool or the decoy pool. (Moved from
  `GEN-002` AC-4 at its PLANNED; see Notes PO-1.)

## Contract

**Module.** `src/server/facility/Steps.luau`, pure.

    export type Steps = {
        tracks: { { number } },   -- tracks[t][i] = machine id; t = 1..procedure_tracks, i = 1..steps_per_track
        finale: { number },       -- { tracks[1][last], tracks[2][last] }, carried for convenience
    }
    Steps.draw(rng: Rng.Rng, layout: Layout.Layout, placement: Machines.Placement,
               assignment: Ring.Assignment, tuning) -> Steps
    Steps.check(steps: Steps, layout: Layout.Layout, placement: Machines.Placement,
                assignment: Ring.Assignment, tuning) -> { string }

- **Class holders** are read through `Ring` (`assignment.keyClasses`,
  `Ring.supplierOf`, `Ring.dependentOf`), never by recomputing σ⁻¹ here.
  `Projection.luau`'s header explains why a second implementation of σ⁻¹ is a
  defect.
- `draw` may produce an invalid candidate. The resample loop lives in
  `Generator` (`GEN-004`). `draw` may still order its choices to raise the
  acceptance rate (for example, choosing the finale pair first), so long as the
  distribution of accepted candidates covers every valid structure, which is
  not asserted.
- Sub-streams: `"choose"`, `"order"`, `"finale"`, derived from the `Rng` passed
  in (`GEN-004` passes the attempt's `"steps"` sub-stream). `draw` derives
  exactly those three labels, once each, and never draws from the rng it is
  handed directly. The same inputs give a deep-equal `Steps`.
- **Purity.** Neither function mutates `layout`, `placement`, `assignment`,
  `tuning` or a `steps` it is given. A `Steps` value is plain data, exactly
  `tracks` and `finale`.
- **Terms.** The *holder* of class `c` is the seated player whose
  `assignment.keyClasses` list contains `c`; at generation each list has one
  entry. The *turner* of a machine is its class's holder. The *helper* of a
  machine is `Ring.supplierOf(assignment, holder)`, the player whose lens is
  `c`. Two classes are *ring neighbours* when `Ring.dependentOf` of one holder
  is the other holder. A machine is a *step* when its id appears in `tracks`,
  and a *decoy* otherwise.
- **`check`** returns **one string per violated invariant**. Each string
  starts with the invariant's name exactly as `tuning.md` writes it, a colon,
  one clause token from the table below (the first violated clause **in the
  table's order** - `shape` before `count`, `rooms` before `ring`, `turn`
  before `read`; amended in RED: "the first clause found" left the token
  implementation-dependent, and the fixtures pin it exactly), then a space
  and free text. A valid candidate returns `{}`. Malformed shapes are reported
  under `INV_balanced_steps:shape`, because a step list of the wrong shape
  cannot satisfy "each class has exactly `stepsPerClass[c]` steps". *Amended
  in RED:* on a malformed shape `check` must not raise, and may either stop at
  the `shape` string or go on to evaluate the other invariants over what is
  present (ids that are in the placement, tracks that are lists, the `finale`
  field when it is two placement ids) - the tests' shape fixtures are built so
  both readings give exactly `{ shape }`, and the empty `{ tracks = {},
  finale = {} }` is only required to *contain* `shape`. `finale` is compared
  **in order**: `{ tracks[2][last], tracks[1][last] }` is a `shape` violation.
  `INV_k_essential:read` is unreachable at generation (one class per player
  makes a lost read a lost turn, and `turn` comes first); it stays in the
  table for a ring where a player holds two classes.

  | prefix:token | clause |
  |---|---|
  | `INV_balanced_steps:shape` | not `procedure_tracks` tracks of `steps_per_track`; an id not in the placement; a machine used twice; `finale` is not `{ tracks[1][last], tracks[2][last] }` |
  | `INV_balanced_steps:count` | some class's step count ≠ `placement.stepsPerClass[c]`, or counts differ by more than 1 |
  | `INV_every_class_has_a_step:missing` | a class in play has no step |
  | `INV_track_alternates:adjacent` | two consecutive steps in one track share a key class |
  | `INV_finale:rooms` | the finale machines share a room, or `Layout.distance` < `paired_room_distance_min` |
  | `INV_finale:ring` | the finale classes' holders are ring neighbours, or the same player |
  | `INV_k_essential:turn` / `:read` | removing some player leaves no step only they can turn / read |

  One fixture usually breaks several invariants (a missing class also breaks
  `INV_balanced_steps:count` and `INV_k_essential`). The tests pin each
  fixture's **exact set** of prefixes, derived by hand.
- **The sweep's inputs** (the same derivation `GEN-004` will nest under its
  attempt): for seed `s` and n, the layout is
  `Layout.generate(Rng.fromSeed(s):derive("layout"), tuning)`; the placement is
  `Machines.generate(Rng.fromSeed(s):derive("machines"), layout, {1..n}, tuning)`;
  the ring is `Ring.assign({"p1".."pn"}, Rng.fromSeed(s))`; and `draw`'s rng is
  `Rng.fromSeed(s):derive("steps")`. *Accepted* means `check` returns `{}`.
  AC-1 to AC-4 and AC-6 run on seeds 1..1000 at each n in {4, 5, 6}. AC-7 runs
  on its own longer sweep (AC-7 text).
- **Measured at planning (PO-2):** across seeds 1..1000 at each n, every
  generated placement admits a finale. Some pair of non-adjacent classes has
  machines in rooms at distance ≥ `paired_room_distance_min` on 1000/1000
  seeds at n = 4, 5 and 6. A sensible `draw` therefore has no structural reason
  to fall near AC-6's floor.

**Oracle partition.**

### The export shape the tests pin

`require("../../src/server/facility/Steps")` must return a table with two
**plain field functions, called with a dot**:

    Steps.draw(rng: Rng.Rng, layout: Layout.Layout, placement: Machines.Placement,
               assignment: Ring.Assignment, tuning: MechanicsTuning.MechanicsTuning) -> Steps
    Steps.check(steps: Steps, layout: Layout.Layout, placement: Machines.Placement,
                assignment: Ring.Assignment, tuning) -> { string }

`tuning` is always the whole `MechanicsTuning` module table (read through
`tuning.instance.<name>`), as in `Layout` and `Machines`.

What the assertions destructure and therefore fix:

- **`Steps` value**: a table with **exactly** the keys `tracks` and `finale`
  and no others. `tracks` is a list of exactly `procedure_tracks` lists, each
  of exactly `steps_per_track` numbers (machine ids of the placement);
  `finale` is exactly `{ tracks[1][last], tracks[2][last] }` **in that
  order** (compared with `Deep.equal`).
- **`draw`**: must call `rng:derive("choose")`, `rng:derive("order")`,
  `rng:derive("finale")` **once each, in any order**, and must not call
  `nextInteger`, `nextNumber` or `shuffle` on the rng it was handed (a
  recording wrapper counts both). Deep-equal on the same seed and inputs. It
  is handed the sweep's worlds (`Layout.generate`, `Machines.generate` with
  classes `{1..n}`, `Ring.assign({"p1".."pn"}, Rng.fromSeed(s))`) for n in
  4, 5, 6, seeds 1..1000 (AC-7 continues past 1000 to about 2,050 at the
  reference's acceptance; the cap is 20,000). It is never handed the hand-built
  fixtures. Over seeds 1..1000 at each n, at least 250 first draws must come
  back with `check == {}`; the reference stub manages 999 / 994 / 983.
  Among the accepted ones the own checker must find nothing - which is the
  same as saying `check` must not accept what the Contract rejects.
- **Classes in play** are the union of `assignment.keyClasses` over
  `assignment.players` (= `1..n`, = the keys of `placement.stepsPerClass`
  in every world the tests build). Holders, helpers and neighbours are read
  through `Ring` as the Terms say; the own checker does the same.
- **`check`**: on every first draw of the sweep (3,000 candidates, accepted
  or not) the DISTINCT set of `<INV>:<token>` heads must deep-equal the own
  checker's, and every string must start with one of the eight heads **then a

### Contract amendments

Three, all in place in `## Contract` with their reason, none touching a
criterion:

1. **"the first clause found" → "the first violated clause in the table's
   order"** (`shape` < `count`, `rooms` < `ring`, `turn` < `read`). Exact
   pinning of a fixture's head set is impossible while the token depends on
   the implementation's search order; the both-finale-clauses fixture pins it.
2. **Malformed shapes: `check` must not raise, and may stop at `shape` or
   evaluate the rest over what is present; `finale` is compared in order.**
   The shape fixtures are built so both readings give exactly `{ shape }`;
   the empty Steps is only required to contain `shape`. Without this, "one
   entry per violated invariant" on a candidate with one track or an unknown
   id was unspecified and a naive `placement.machines[id].keyClass` would
   raise.
3. **`INV_k_essential:read` is unreachable at generation** and stays in the
   table for a two-class holder. With one class per player a lost read is a
   lost turn, and `turn` comes first - so no fixture produces `read`, and the
   missing-class fixture pins `turn`. Stated so GREEN does not hunt for a
   `read` case that cannot exist.

Also read, not amended: AC-3's "when n ≥ 4" is always true at n ∈ {4, 5, 6},
so the ring clause is asserted unconditionally.

**Design.**
- `draw` derives `"finale"`, `"choose"` and `"order"`, once each, and takes no
  direct draws.
  1. *Finale.* It lists every ordered machine pair that satisfies `INV_finale`:
     the rooms differ, `Layout.distance ≥ paired_room_distance_min` (memoised
     per room pair), and the holders are distinct and not ring neighbours via
     `Ring.dependentOf`. It picks one uniformly from `"finale"`. Ordered pairs
     mean the same pick decides which track closes on which machine. If no
     pair qualifies, it falls back to any pair of different classes, which
     `check` then rejects.
  2. *Choose.* For each class in play, it shuffles the class's other machines
     with `"choose"` and takes the first `stepsPerClass[c]` minus any finale
     use.
  3. *Order.* It shuffles the leading steps with `"order"`. A depth-first
     search then finds the first arrangement in that order where every track
     alternates, including the last leading step against the finale machine.
  - No step reads `requiredSetting` (AC-7).
  - This differs from the reference stub, which picks a class pair first and
    then looks for a machine pair. Enumerating machine pairs directly cannot
    pick a class pair that has no far-enough machines, so the reference's
    `rooms` rejections do not occur.
- **Holders through `Ring`.** Holders are read from `assignment.keyClasses` over
  `assignment.players`. Helpers come from `Ring.supplierOf` and neighbours from
  `Ring.dependentOf`. σ is not read directly and σ⁻¹ is not recomputed.
- **`check`.**
  - It returns one string per invariant, headed by the first violated clause in
    table order.
  - On a malformed candidate it does not raise. It evaluates the other
    invariants over what is present, the same reading as the own checker.
  - `finale` is compared with the tracks' last steps in order.
- `draw` raises if `procedure_tracks ≠ 2`, because the finale is a pair. Today's
  constant is 2 (derived), so this is outside what the tests can reach.
