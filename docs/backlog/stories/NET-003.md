## Context

The fifth and last check of the pipeline, and B4's fourth adversarial case: a call
arriving at a hundred per second. Without it, every remote is a denial-of-service
surface and every in-game budget is advisory.

It has a second job that is not defensive. `tuning.md` §3 gives
`signal_rate_limit_seconds` = 1.5 as **derived**, serving two purposes at once: it
keeps the shared signal stream readable at `players_max` senders, and it satisfies
B4's requirement that every remote be rate-limited. The same mechanism is a game
rule and a security control, which is unusual and worth knowing — it means a story
that "relaxes the rate limit for responsiveness" is changing the game's difficulty.

The limiter is driven by the **injected clock** from `ROUND-001`, so the whole of
it is tested in simulated time with no waiting. A rate-limit test that sleeps is a
slow test that eventually flakes on CI hardware.

**Which required gate would fail if this story's artifact broke:** `unit`.

## Acceptance criteria

- **AC-1** — Given a remote with `minIntervalSeconds = 1.5` and a clock at `t`,
  when a seated player calls it at `t`, then it is accepted; when the same player
  calls again at `t + 1.4`, then it is rejected with reason `"rate"`; and when they
  call at `t + 1.5`, it is accepted.
  *Semantics:* the comparison is `now - lastAccepted >= minIntervalSeconds`,
  inclusive. Exactly at the interval the call goes through.
- **AC-2** — Given two players, when player A is rate-limited, then player B's call
  at the same instant is accepted.
  *Control:* an implementation with one shared last-call timestamp passes AC-1 and
  **must** fail this. It is a one-word difference in the implementation and it would
  make one fast player mute everybody else.
- **AC-3** — Given a rejected call, when the next call from that player arrives,
  then the interval is measured from the last **accepted** call, not the last
  attempted one.
  *Control:* an implementation that updates the timestamp on rejection **must** fail
  this — under it, a player calling continuously at 100 Hz is locked out forever
  rather than being served every 1.5 seconds. That turns a rate limit into a
  self-inflicted denial of service.
- **AC-4** — Given a remote declared with no `rateLimit`, when it is called
  repeatedly, then every call is accepted.
- **AC-5** — Given a call that fails identity, shape, range or phase, when it is
  guarded, then the limiter's state for that player is **not** advanced.
  *Semantics:* rate is check 5 of 5. A malformed flood must not consume the
  attacker's own budget in a way that would also throttle their legitimate calls —
  and more importantly, must not be silently absorbed before `TEL-003` can count
  it as malformed.
- **AC-6** — Given a player who leaves the round, when the limiter is asked to
  forget them, then their entry is removed, and the limiter's stored entry count
  after a full round of joins and leaves equals the number of currently seated
  players.
  *Semantics:* the limiter keys on player id and a server runs for days. An
  unbounded table keyed by every player who ever connected is a memory leak with a
  slow fuse.

### `src/net/RateLimiter.luau`

    export type RateLimiter = {
        allow:  (self: RateLimiter, playerId: PlayerId, key: string, now: number) -> boolean,
        forget: (self: RateLimiter, playerId: PlayerId) -> (),
        size:   (self: RateLimiter) -> number,          -- entries held; AC-6 reads this
    }

    RateLimiter.new(minIntervalSeconds: number) -> RateLimiter

`key` is the remote name, so one player's limit on one remote is independent of
their limit on another. `now` is passed in; the limiter never reads a clock, and
`ROUND-001`'s source guard would catch it if it did — `os.clock`, `tick` and
`math.random` are refused in every `src/` module but their one adapter, and the
guard enumerates through the classifier, so it covers this file the moment it
exists without anyone adding it to a list.

**`allow` records the timestamp only when it returns `true`.** That single line is
AC-3.

**`PlayerId` is re-declared here, not imported from `Wrapper`.** `Wrapper` will
require `RateLimiter`, and the reverse edge would be a cycle. It is the same
string alias.

### What the limiter stores, and what `size()` counts

**One entry per PLAYER, holding a timestamp per key.** Not one entry per
`(player, key)` pair:

    entries: { [PlayerId]: { [string]: number } }
    size()  -> the number of PLAYERS held
    forget(playerId) -> removes that player's whole entry, every key with it

This is pinned because AC-6 is phrased in terms of it and the two shapes are a
one-line difference that no other criterion can tell apart: *"the limiter's stored
entry count after a full round of joins and leaves equals the number of currently
seated players"* is true under this shape whatever mix of remotes each player
called, and false under a `(player, key)` table for any player who used two
remotes. A `size()` that counts pairs would make AC-6 read as a statement about
how many remotes the test happened to exercise, which is not a property of
anything. `forget` taking a player and dropping all their keys is the same
decision seen from the disconnect side — a leaver stops existing, and "per
remote" is not a question anyone asks about a player who has gone.

### How `Wrapper.guard` obtains a limiter — and why it is not injected

`guard` constructs **one limiter per `guard()` call**, in the enclosing scope of
the returned closure, when and only when `definition.rateLimit ~= nil`:

    local limiter = if definition.rateLimit ~= nil
        then RateLimiter.new(definition.rateLimit.minIntervalSeconds)
        else nil
    return function(playerId, rawArgs) ... end

so its state persists across calls to one guarded function — a limiter built
*inside* the closure would be new on every call and could never reject anything.
The key passed to `allow` is `definition.name`.

**Not through `GuardContext`, and this was checked rather than assumed.** Adding
a `limiter` field to `GuardContext` is the design that lets a driver call
`forget` on a disconnect, and it is the one this story does **not** take, for a
reason measured against the tree on 2026-09-22: every `GuardContext` in
existence is built by two frozen test helpers — `NetContract.context()`
(`NetContract.luau:133`) and `PhaseContract.world()` (`PhaseContract.luau:117`)
— and neither may be edited outside RED. A required field would make `guard`
index a nil on all of `NetContract`'s and `PhaseContract`'s checks; an optional
one is a signature change with a caller list, which this story's scope denies.
The tests are not typechecked either (the `typecheck` gate runs over `src` only),
so the failure would arrive at runtime across two merged stories rather than as
a compile error.

**The consequence, stated rather than discovered later:** under this design
`forget` and `size` are reachable from tests and from a future driver that holds
its own limiter, but **no current production path calls them**. AC-6 is a unit
criterion on `RateLimiter`, which is exactly how it is phrased ("when the limiter
is asked to forget them"). Wiring a disconnect to `forget` belongs to the M3
driver and to `SEAT-003`, and until then the leak AC-6 guards against cannot
occur, because nothing in production holds a limiter across rounds. This is the
same "declared early, consumed later" move `NET-001` made with `legalPhases` and
`rateLimit` themselves, and it is recorded here so the next story does not read
`forget`'s absence from production as an oversight.

### `context.clock.now()` is read per call that reaches check 5, and not before

The parallel of `NET-002`'s read-count pin, one position later, and the reason is
the same: *"after phase"* is only observable if something counts. For a remote
that **declares** a `rateLimit`:

- `context.clock.now()` is read **0 times** on a call identity, shape, range or
  phase has already rejected. This is AC-5's structural form: a limiter that is
  never consulted cannot have advanced.
- it is read **at least once** on a call that reaches check 5, and the value
  compared is the one that call returned — not one captured when `guard` was
  called. A captured clock is `NET-002`'s captured phase wearing a different hat,
  and it passes every test that never advances time.

For a remote with **no** `rateLimit`, `context.clock.now()` is read **0 times,
ever**: AC-4's structural form. Not constrained: whether the clock is read during
`guard()` construction (it must not be *compared*, but reading it is not
forbidden), or read more than once per call.

### `detail` for a rate rejection

As with `NET-002`'s phase rejection, the wrapper builds this `Rejection` itself —
no schema is in the path — so **`detail` carries no `"rate: "` prefix**. `reason`
already names the check that fired, and a second encoding is one a later refactor
can let drift.

What it must carry, because `TEL-003` emits it and an operator reads it when a
spike appears: **the remote's name and the interval that was required.** The
pinned case: a remote declared `{ minIntervalSeconds = 1.5 }` under a unique
name, called twice inside the interval — `detail` is non-empty, does **not** match
`^rate:`, contains the remote's name as a plain substring, and contains `1.5`.
Wording otherwise free.

*Deliberately not pinned:* how long the caller actually waited. It is the obvious
second number and it is a float difference (`t + 1.4` minus `t` is not exactly
`1.4` in binary floating point), so a substring assertion on it would pin the
formatting of a rounding error. An implementation is free to include it.

**One provenance assertion, and its vacuity checks.** So that the `1.5` in the

### Why an interval and not a token bucket

A minimum interval is what `tuning.md` specifies (`signal_rate_limit_seconds`),
and it is the right shape for this game: a token bucket permits a burst, and a
burst of signals is exactly the thing the constant exists to prevent — the shared
stream stops being readable at `players_max` senders. Scarcity is handled
separately and far more strictly by `signal_budget_per_player`, which is the
binding constraint "by two orders of magnitude". If a later remote wants burst
tolerance, that is a new limiter alongside this one, argued in its own story.

### No test in this story may sleep, wait, or read real time

The clock is injected precisely so that a hundred calls at 10 ms intervals is an
instant test. A rate-limit suite that takes eight seconds is a suite that starts
flaking on CI hardware, and this is the one story where writing `task.wait` would
feel natural. Time moves only through `Clock.manual`'s `advance` and `set`.

## Out of scope

- Any global or per-server rate limit. Per player, per remote, and nothing else.
- Banning, kicking or escalation on repeated violation. A rejection is a rejection;
  what an operator does about a spike is an M5/M6 decision informed by `TEL-003`.
- Burst tolerance or token buckets. Argued against above.
- The signal budget (`signal_budget_per_player`). A game resource, not a rate
  limit, and M3.
- Client-side throttling. It would be a courtesy to honest clients and worth
  nothing against hostile ones.

## Game design

Implements the security half of `tuning.md` §3's `signal_rate_limit_seconds` (1.5,
**derived**) ahead of the signal remote that will use it. The constant's own
rationale names both purposes, so this story introduces no new constant and
changes none.

The design property to preserve: the limiter is **not a scarcity mechanism**. If a
later story finds itself tuning this number for game balance rather than for stream
readability, that is a signal the budget is doing the wrong job and belongs in a
conversation with the Game Designer, not in this module.

## Notes
### PO decisions made at PLANNED

**PO decision 1 — the limiter stores one entry per PLAYER, and `size()` counts
players.** AC-6 says the stored entry count equals the number of currently seated
players. Under a `(player, key)` table that is false for any player who used two
remotes, and the criterion would degrade into a statement about how many remotes
the test happened to exercise. Pinned in the Contract rather than amended into
the criterion, because the criterion is right and it is the *shape* that was
underdetermined. The `sizeCountsKeys` control exists to make the other shape
fail something.

**PO decision 2 — the limiter is constructed inside `guard`, not injected
through `GuardContext`.** The injected design is the one that lets a driver call
`forget` on a disconnect, and it was rejected here on evidence rather than taste:
every `GuardContext` in the tree is built by two **frozen** test helpers
(`NetContract.luau:133`, `PhaseContract.luau:117`), the tests are not
typechecked (the gate runs over `src` only), so a required field would surface as
a runtime nil across two merged stories' suites, and an optional field is a
signature change this story's scope denies. Recorded with its consequence:
`forget` and `size` have no production caller until the M3 driver exists, which
is the same "declared early, consumed later" move `NET-001` made with
`legalPhases`. Nothing is silently dead — AC-6 is a unit criterion on
`RateLimiter` and is phrased that way.

**PO decision 3 — `signal_rate_limit_seconds` does NOT go into
