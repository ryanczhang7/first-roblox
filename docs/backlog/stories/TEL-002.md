## Context

`TEL-001` built the envelope and emitted nothing. This story adds the emitters to
the phase machine, as `Emit` effects returned from `step` — so the events are part
of the machine's tested output rather than a side channel nobody asserts on
(`architecture.md` §6, D3).

Six of B6's nine events are emittable from a server round with no persistence.
Three — `day_n_return`, `co_play_with_known_player`, `purchase` — need a store and
are M5; `TEL-001` already declared their buckets so M5 adds an emitter rather than
a vocabulary.

`bounce_before_resolution` is the one to get exactly right. A5 makes first-play
bounce a **direct ranking penalty**: "a player who leaves before a round resolves
is a direct ranking penalty". It is simultaneously the most valuable event in the
list and the easiest to emit twice or not at all, because a player leaving produces
one event and several state changes.

**Which required gate would fail if this story's artifact broke:** `unit`.

## Acceptance criteria

- **AC-1** — Given a player joining a lobby, when the event is applied, then
  exactly one `join` event is emitted, bucket D1, carrying that player's id; and
  when a duplicate `PlayerJoined` for the same player is applied, no second `join`
  is emitted.
- **AC-2** — Given a round reaching `Resolution` with any outcome, when the
  transition occurs, then exactly one `round_complete` event is emitted, bucket
  D2_7, carrying the outcome's `result` and `reason` and the round id.
- **AC-3** — Given a round reaching `Resolution` with `result = "no_contest"`, when
  the events are inspected, then `round_complete` still carries
  `result = "no_contest"` and is distinguishable from a loss by that field alone.
  *Semantics:* a lobby collapse must not be counted as a played round in retention
  reporting. Under amendment 9 progression is shared, so a `no_contest` counted as
  a loss would misreport the group's record as well as the metric.
- **AC-4** — Given a player leaving while the phase is `Lobby`, `Assignment` or
  `Round`, then exactly one `bounce_before_resolution` event is emitted for that
  player, bucket D1, carrying the phase they left in.
- **AC-5** — Given a player leaving while the phase is `Resolution` or `Post`, then
  **no** `bounce_before_resolution` is emitted.
  *Control:* an implementation emitting on every `PlayerLeft` passes AC-4 and
  **must** fail this. Since A5 makes this event a ranking penalty, the failure
  direction matters: over-reporting a bounce is self-harm.
- **AC-6** — Given a player who leaves during `Round` and then leaves again via a
  duplicate event, then exactly one `bounce_before_resolution` is emitted for them
  in that round; and given a player who leaves in one round and again in the next,
  then one is emitted per round.
- **AC-7** — Given a round that completes and a player who was in their first
  round, when `Resolution` is reached, then exactly one `first_round_complete`
  event is emitted for that player, bucket D1, and none is emitted for a player on
  a later round.
  *Semantics:* "first round" is per session — the machine knows how many rounds a
  player has been seated for since joining, and nothing more. Cross-session first
  play needs persistence and is M5. **Say so in the event's `fields` with a
  `scope = "session"` marker**, so an M5 story replacing it knows what it is
  replacing.
- **AC-8** — Given a `RematchAccepted` event in `Post`, then exactly one
  `rematch_accepted` event is emitted, bucket D2_7; and given a player leaving
  during `Post` instead, then one `session_end` is emitted for them, bucket D1.
- **AC-9** — Given a full lifecycle driven end to end, when every `Emit` effect is
  collected, then each event's `at` equals the `now` of the step that produced it,
  and the sequence contains no event whose name is absent from `Event.BUCKETS`.
  *Control:* an implementation using a real clock for `at` **must** fail this under
  a manual clock.

## Contract

Changes `src/server/round/PhaseMachine.luau` only, plus the state it carries to
answer AC-6 and AC-7.

**`RoundState` gains two fields** — a signature change to an exported type, with
callers grepped before dispatch:

    bounced:      { [PlayerId]: boolean },   -- reset on entering Lobby
    roundsSeated: { [PlayerId]: number },    -- survives across rounds within a session

| Caller | File | What changes |
|---|---|---|
| `PhaseMachine.initial` | `src/server/round/PhaseMachine.luau` | initialises both |
| `PhaseMachine.step` | same | maintains both |
| ROUND-003 suite | `tests/server/round/phase_machine_test.luau` | state construction helpers |
| ROUND-004 suite | `tests/server/round/lobby_test.luau` | same |
| ROUND-005 suite | `tests/server/round/ending_test.luau` | same |

No change to `step`'s signature. `Effect` already carries `Emit`.

### `sessionId`

A `sessionId` is needed for the envelope and is **not** a round id: it identifies
this server instance's run, so that D1/D2–7/D8–28 bucketing has something stable to
hang on. It is passed into `PhaseMachine.initial` and carried in `RoundState`. It
is generated by the driver, not by the machine, because generating it would make
`step` impure.

### The six emitters, and exactly where each fires

| Event | Fires | At most once per |
|---|---|---|
| `join` | `PlayerJoined` accepted (not a duplicate, not over `players_max`) | player per session |
| `first_round_complete` | entering `Resolution`, for each seated player whose `roundsSeated` is 1 | player per session |
| `round_complete` | entering `Resolution` | round |
| `bounce_before_resolution` | `PlayerLeft` while phase ∈ {Lobby, Assignment, Round} | player per round |
| `rematch_accepted` | `RematchAccepted` in `Post` | player per round |
| `session_end` | `PlayerLeft` while phase ∈ {Resolution, Post} | player per round |

A single `PlayerLeft` produces **either** a bounce **or** a session end, never both
and never neither. That is the rule AC-4 and AC-5 pin between them.

## Deferred verifications

None. The phase machine is pure and the clock is injected, so every case is
constructible.

## Model guidance

**Resolved model of every dispatch, by name:** _(record at dispatch.)_

Brief RED that **exactly-once is the hard part of this story**, not the event
shapes. Five of the nine criteria are about an event firing once rather than twice
or never, and the natural test — drive the lifecycle, assert the event is present —
cannot see a double emission. Assert **counts**, not presence.

## Out of scope

- `day_n_return`, `co_play_with_known_player`, `purchase`. Declared in `TEL-001`'s
  bucket mapping, emitted in M5 when there is a store.
- Cross-session "first round". AC-7 is session-scoped and says so in its own
  payload.
- A real sink. `TEL-001` §Out of scope.
- Any aggregation, dashboard or report. The events are emitted; reading them is an
  operator activity in M6.
- Signal, actuation and instability telemetry. M3, with those mechanics.
- Remote-rejection telemetry. `TEL-003`.

## Game design

Implements brief **B6** and **A5**'s three discovery buckets for the events a
server round can observe.

No tuning constant is introduced. One is *waiting on this story*:
`disconnect_grace_seconds` (30, **placeholder**) is to be replaced "with observed
reconnect times once telemetry exists (B6)" — that is these events. Record in the
story's `## Notes` that the data path for that replacement now exists, so the
Game Designer can ask for it rather than guessing again.

The design decision AC-3 protects: under amendment 9, players win or lose together
and a `no_contest` is explicitly **not** a loss — "the group did not fail, the
lobby did". A metric that flattens the two would misreport both the ranking signal
and the group's own record.
