## Context

`TEL-001` built the envelope and emitted nothing. This story adds the emitters to
the phase machine, as `Emit` effects returned from `step` — so the events are part
of the machine's tested output rather than a side channel nobody asserts on
(`architecture.md` §6, D3).

Six of B6's nine events are emittable from a server round with no persistence.
Three — `day_n_return`, `co_play_with_known_player`, `purchase` — need a store and
are M5; `TEL-001` already declared their buckets so M5 adds an emitter rather than
a vocabulary.

`bounce_before_resolution` is the one to get exactly right. A5 makes first-play
bounce a **direct ranking penalty**: "a player who leaves before a round resolves
is a direct ranking penalty". It is simultaneously the most valuable event in the
list and the easiest to emit twice or not at all, because a player leaving produces
one event and several state changes.

**Which required gate would fail if this story's artifact broke:** `unit`.

## Acceptance criteria

- **AC-1** — Given a player joining a lobby, when the event is applied, then
  exactly one `join` event is emitted, bucket D1, carrying that player's id; and
  when a duplicate `PlayerJoined` for the same player is applied, no second `join`
  is emitted.
- **AC-2** — Given a round reaching `Resolution` with any outcome, when the
  transition occurs, then exactly one `round_complete` event is emitted, bucket
  D2_7, carrying the outcome's `result` and `reason` and the round id.
- **AC-3** — Given a round reaching `Resolution` with `result = "no_contest"`, when
  the events are inspected, then `round_complete` still carries
  `result = "no_contest"` and is distinguishable from a loss by that field alone.
  *Semantics:* a lobby collapse must not be counted as a played round in retention
  reporting. Under amendment 9 progression is shared, so a `no_contest` counted as
  a loss would misreport the group's record as well as the metric.
- **AC-4** — Given a player leaving while the phase is `Lobby`, `Assignment` or
  `Round`, then exactly one `bounce_before_resolution` event is emitted for that
  player, bucket D1, carrying the phase they left in.
- **AC-5** — Given a player leaving while the phase is `Resolution` or `Post`, then
  **no** `bounce_before_resolution` is emitted.
  *Control:* an implementation emitting on every `PlayerLeft` passes AC-4 and
  **must** fail this. Since A5 makes this event a ranking penalty, the failure
  direction matters: over-reporting a bounce is self-harm.
- **AC-6** — Given a player who leaves during `Round` and then leaves again via a
  duplicate event, then exactly one `bounce_before_resolution` is emitted for them
  in that round; and given a player who leaves in one round and again in the next,
  then one is emitted per round.
- **AC-7** — Given a round that completes and a player who was in their first
  round, when `Resolution` is reached, then exactly one `first_round_complete`
  event is emitted for that player, bucket D1, and none is emitted for a player on
  a later round.
  *Semantics:* "first round" is per session — the machine knows how many rounds a
  player has been seated for since joining, and nothing more. Cross-session first
  play needs persistence and is M5. **Say so in the event's `fields` with a
  `scope = "session"` marker**, so an M5 story replacing it knows what it is
  replacing.
- **AC-8** — Given a `RematchAccepted` event in `Post`, then exactly one
  `rematch_accepted` event is emitted, bucket D2_7; and given a player leaving
  during `Post` instead, then one `session_end` is emitted for them, bucket D1.
- **AC-9** — Given a full lifecycle driven end to end, when every `Emit` effect is
  collected, then each event's `at` equals the `now` of the step that produced it,
  and the sequence contains no event whose name is absent from `Event.BUCKETS`.
  *Control:* an implementation using a real clock for `at` **must** fail this under
  a manual clock.

### 2. `sessionId`

It identifies this server instance's run, not a round, so that D1/D2–7/D8–28
bucketing has something stable to hang on. The driver generates it, not the
machine, because generating it inside the machine would make `step` impure. It
is carried unchanged across every transition, including `Post → Lobby`, and is
the `sessionId` of every event this state emits.

### 3. The six emitters: exactly when each fires, and its payload

`E(name, playerId, fields)` means
`{ kind = "Emit", event = Event.new(name, now, state.sessionId, playerId, fields) }`,
where `now` is the `now` argument of the `step` that produced it. The step never
uses another time source.

| Event | Fires when | playerId | fields | Guard (at most once per) |
|---|---|---|---|---|
| `join` | `PlayerJoined` is **accepted** (seated), and `roundsSeated[p] == nil` | p | `{}` | player per session. Accepting the join sets `roundsSeated[p] = 0` if absent, and clears `departed[p]` (P2a) |
| `bounce_before_resolution` | `PlayerLeft` for a **seated** p, phase ∈ {Lobby, Assignment, Round}, `departed[p]` not set | p | `{ phase = <phase left in> }` | player per round. Sets `departed[p]` |
| `session_end` | `PlayerLeft` for a **seated** p, phase ∈ {Resolution, Post}, `departed[p]` not set | p | `{ phase = <phase left in> }` | player per round. Sets `departed[p]` |
| `round_complete` | the step that **enters** `Resolution`, by any of the three paths (`RoundResolved`, quorum on `Tick` or `PlayerLeft`, clock) | nil | `{ roundId, result, reason }` from the recorded outcome | round |
| `first_round_complete` | the same step, for each p in `players` (seat order) with `roundsSeated[p] == 1` and `departed[p]` not set | p | `{ roundId, scope = "session" }` | player per session, because `roundsSeated` only grows |
| `rematch_accepted` | `RematchAccepted` in `Post` from a **seated** p with neither `departed[p]` nor `rematched[p]` set | p | `{ roundId }` | player per round. Sets `rematched[p]` |

`roundsSeated[p]` goes up by 1 for every p in `players` on the step that
**enters `Round`** (`SeatsAssigned`). It is never reset or decremented.

**P1 — "seated" is the gate for every per-player event.** A `PlayerLeft` or
`RematchAccepted` naming someone not in `players` emits nothing, just as the
machine already ignores it. A player the lobby refused (over `playersMax`) was
never joined and so never bounces.

**P2 — a `PlayerLeft` produces exactly one of {bounce, session end} or, if
`departed[p]` is already set, neither.** AC-4 and AC-5 pin this between them.
One guard map serves both events. The planned `bounced` field is renamed
`departed` because it now guards `session_end` as well.

**P2a — an accepted `PlayerJoined` clears `departed[p]`.** A join is accepted
only in `Lobby`, so this concerns one case only: a player who leaves the Lobby
and rejoins it before the round starts. That player is present, so they must
still get their `first_round_complete`. If they leave again, that is a second
real departure and emits a second bounce. "At most once per round" therefore
means *once per departure*: a duplicate `PlayerLeft` with no accepted join
between the two (AC-6's case) emits nothing.

**P3 — the state changes a `PlayerLeft` makes are unchanged from ROUND-004/005.**
Only Lobby and Round unseat. A player leaving in Assignment, Resolution or Post
**stays in `players`**, which is existing behaviour and not this story's to
change. `departed` is what stops such a player collecting a second bounce, a
`first_round_complete` or a `rematch_accepted`. (That the player stays seated at
all is recorded in `## Notes` as a finding for SEAT-003's disconnect work.)

**P4 — `rematch_accepted` gets its own guard map (`rematched`).** The planned
contract promised "at most once per player per round" but gave it no state to
keep that promise.

**P5 — effect ORDER within one step is pinned**, because a trace or a sink that
reads the list reads it in order:

| Step | Effects, in this order |
|---|---|
| accepted `PlayerJoined` | `join` (first in session only), else nothing |
| `Tick` Lobby → Assignment | `AssignSeats`, and nothing else |
| `SeatsAssigned` | nothing |
| `PlayerLeft` (no phase change) | `bounce_before_resolution` or `session_end`, or nothing |
| any step entering `Resolution` | [the leaver's `bounce_before_resolution`, if this is a quorum-ending `PlayerLeft`], then `round_complete`, then `first_round_complete` × n in seat order |
| `Tick` Resolution → Post | `ComputeTrace`, and nothing else |
| `RematchAccepted` in Post | `rematch_accepted`, or nothing |
| `Tick` Post → Lobby | `PromptRematch`, and nothing else |

So the *control* effects (every kind but `Emit`) are exactly what ROUND-003/004/005
pinned. Only `Emit`s are added.

## Game design

Implements brief **B6** and **A5**'s three discovery buckets for the events a
server round can observe.

No tuning constant is introduced. One is *waiting on this story*:
`disconnect_grace_seconds` (30, **placeholder**) is to be replaced "with observed
reconnect times once telemetry exists (B6)" — that is these events. Record in the
story's `## Notes` that the data path for that replacement now exists, so the
Game Designer can ask for it rather than guessing again.

The design decision AC-3 protects: under amendment 9, players win or lose together
and a `no_contest` is explicitly **not** a loss — "the group did not fail, the
lobby did". A metric that flattens the two would misreport both the ranking signal
and the group's own record.
