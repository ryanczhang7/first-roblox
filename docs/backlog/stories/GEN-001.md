## Context

Epic: `EPIC-04`. The facility is `room_count` rooms joined by doorways
(`mechanics.md` §1, G1–G2). Rooms are cells of a `layout_grid_columns` ×
`layout_grid_rows` grid. Doorways join only grid-adjacent rooms: a uniformly
random spanning tree first, then each other adjacent pair with probability
`layout_loop_door_chance`. Every player spawns in `spawn_room`, the room of least
eccentricity, with ties going to the lowest index. `INV_layout` states the
structural invariant (`tuning.md` §2).

The whole generator is built on distances: par, `INV_finale`'s
`paired_room_distance_min`, and the trace. This story builds the room graph and
the distance function everything else reads.

**Which required gate would fail if this story's artifact broke:** `unit`.

## Acceptance criteria

- **AC-1** — Given every seed `1..1000` (`Rng.fromSeed(seed)`) and the shipped
  `MechanicsTuning`, when `Layout.generate` runs, then `INV_layout` holds and
  `Layout.check` returns `{}`. There are exactly `room_count` rooms on distinct
  cells of the grid. Every doorway joins two grid-adjacent rooms, and no pair
  has two doorways. The doorway graph is connected. Every room has degree ≤ 4.
  Some pair of rooms is at least 2 edges apart.
  *Control:* `Layout.check` must report `INV_layout` for each of four hand-built
  violations, naming the broken clause (tokens pinned in `## Contract`): two
  rooms on one cell, a diagonal doorway, a disconnected pair, and 5 rooms.
  Each violation must be reported under its own clause token.
- **AC-2** — Given the same seed and tuning, when `generate` runs twice, then
  the layouts are identical (deep-equal). Across the AC-1 sweep, at least 20
  distinct occupied-cell **sets** appear. A set is the `(column, row)` pairs
  themselves, not a translated shape. The 3 × 3 grid has 48 connected 6-cell
  sets.
  *Control:* a generator that always occupies the same six cells must fail the
  second clause, scoring 1.
- **AC-3** — Given the fixed 2 × 3 block of six cells, which has exactly 15
  spanning trees, when `Layout.spanningTree` draws 150,000 trees, draw `i` from
  `Rng.fromSeed(1):derive("tree-" .. i)`, then all 15 trees appear and each
  appears with frequency within 1/15 ± 0.004 (about 6 standard errors).
  *Controls:* a tree built by breadth-first search from cell 1 (one tree,
  always) must fail, scoring about 1.0 for one tree. A random-order Kruskal
  (shuffle the edges, keep each that joins two components) must fail: its rarest
  tree scores about 0.059 (measured at planning, Note PO-2).
- **AC-4** — Given a hand-built layout with known shortest paths, including one
  with a loop and one that is a chain, when `Layout.distance(a, b)` is called
  for every pair, then it returns the number of doorway edges on a shortest path.
  The answer is 0 for `a = b` and symmetric. On the same fixtures,
  `Layout.neighbours` returns each room's door-neighbours in ascending order.
- **AC-5** — Given hand-built layouts, when `Layout.spawnRoom` is called, then it
  returns the room of least eccentricity. When eccentricities tie, it returns
  the lowest room index. One fixture must have a tie in which the tied rooms do
  not include room 1. Across the AC-1 sweep, every generated layout's
  `spawnRoom` field equals `Layout.spawnRoom` of that layout.
- **AC-6** — Given every seed `1..10000`, when extra doorways are counted, then
  a ratio lies within `layout_loop_door_chance` ± 0.03. The numerator is the
  total of non-tree doorways (`#doors - (room_count - 1)`). The denominator is
  the total of non-tree adjacent pairs (grid-adjacent occupied pairs minus
  `(room_count - 1)`).
  *Controls:* a generator that never adds a loop door must fail, scoring 0. A
  generator that adds every loop door must fail, scoring 1.

## Contract

RED may amend any block below **in place**, with a one-line reason under it.
GREEN builds what the amended block says.

**Module.** `src/server/facility/Layout.luau`, `--!strict`, pure. It requires
only `src/shared/Rng.luau` and `src/shared/MechanicsTuning.luau` (types and
values). It never mutates its arguments.

    export type Cell = { column: number, row: number }               -- 1-based
    export type Room = { id: number, column: number, row: number }   -- 1-based cell
    export type Door = { a: number, b: number }                       -- room ids, a < b; doors sorted by (a, b) ascending
    export type Layout = { rooms: { Room }, doors: { Door }, spawnRoom: number }

    Layout.generate(rng: Rng.Rng, tuning: MechanicsTuning.MechanicsTuning) -> Layout
    Layout.check(layout: Layout, tuning: MechanicsTuning.MechanicsTuning) -> { string }
    Layout.distance(layout: Layout, a: number, b: number) -> number
    Layout.neighbours(layout: Layout, id: number) -> { number }  -- ascending
    Layout.spawnRoom(layout: Layout) -> number
    Layout.spanningTree(rng: Rng.Rng, cells: { Cell }) -> { Door }  -- exported for AC-3

- **Room ids** run `1..room_count` in row-major order of their cells (row first,
  then column), and `rooms[i].id == i`. Every tie-break in the generator uses
  this id (`mechanics.md` §1).
- **`spanningTree`'s door ids are indices into its `cells` argument.** Each has
  `a < b`, and the doors are sorted by `(a, b)`. It returns `#cells - 1` doors.
  It consumes the `rng` it is handed directly and derives nothing. `generate`
  passes the occupied cells in room-id order, so its indices are room ids.
  Precondition: the cells are distinct and grid-connected. Behaviour otherwise
  is unspecified.
- **Occupied cells** are grown from a uniformly drawn start cell, adding a
  uniformly drawn free cell that is grid-adjacent to the occupied set, until
  there are `room_count` cells. This is an implementation choice, pinned here
  for determinism. Only `INV_layout` and AC-2's variety are specified, and no
  test may pin which cells a given seed produces.
- **The spanning tree** is uniform over spanning trees of the occupied cells'
  adjacency graph. Wilson's algorithm (loop-erased random walks, rooted at cell
  1) satisfies this. Random edge order with union-find does not, and AC-3
  measurably rejects it (PO-2).
- **Loop doors.** Every grid-adjacent occupied pair that is not a tree door gets
  a door when `loops:nextNumber() < layout_loop_door_chance`. There is one draw
  per pair, in `(a, b)` order.
- **Randomness.** `generate` is handed an `Rng` the caller has already derived
  (`GEN-004` passes the attempt's `"layout"` sub-stream). It derives exactly the
  labels `"cells"`, `"tree"` and `"loops"` from it, and draws from nothing else.
- **`check`** returns one string per violated clause. Each string **starts with**
  `INV_layout:`, then one of the clause tokens below, then a space and free text.

  | token | clause |
  |---|---|
  | `room_count` | `#rooms ~= room_count`, or `rooms[i].id ~= i` |
  | `cells` | two rooms share a cell, or a cell lies outside the grid |
  | `adjacency` | a door joins two rooms that are not grid-adjacent, names an unknown room, or repeats a pair |
  | `connected` | the doorway graph is not connected |

  A valid layout returns `{}`. Each AC-1 control must produce its own token. The
  5-room control is otherwise valid (connected and adjacent), so it produces
  `room_count` and nothing else. The degree and distance-≥-2 consequences are
  asserted on generated layouts, not by `check`.
- **Distances** are breadth-first search over doors. An unreachable pair returns
  `math.huge`. An id outside `1..#rooms` is an error. Memoising is allowed, but
  never inside the `Layout` value, which stays plain data (AC-2 deep-equals it).
- **`spawnRoom`** = argmin over rooms of `max_b distance(a, b)`, ties to the
  lowest id.

**Oracle partition.**
- *Mechanical, exact pinning:* AC-1, AC-2's first clause, AC-4, AC-5, and the
  `check` tokens. Fixtures are hand-built. Their expected values are derived by
  hand in the test, never computed by `Layout`.
- *Settled number read out:* AC-3's 15 trees of the 2 × 3 ladder, and AC-2's 48
  connected 6-sets. Both were enumerated at planning (Notes PO-2, PO-3). The 15
  trees are a fixture list written by hand, not generated by the code under
  test.
- *Oracle-free with negative control:* AC-2's variety (≥ 20 sets), AC-3's
  uniformity, and AC-6's loop rate. Each statistic is a pure function in a test
  helper. It runs over both the real module and the hand-written wrong
  generators. The controls need only `Rng`, which is merged, so they run **in
  RED**: record the measured value of each in the handoff. The tolerances are
  the Lead PO's. RED may tighten them from a measured variance, but may not
  widen them.

**Callers of changed signatures.** None. `Layout` is a new module, and no
existing export's signature changes (`Rng` and `MechanicsTuning` are only read).
Checked with `rg -n "facility/Layout|Layout\." src tests` on 2026-09-30: no
hits. RED's handoff must state that it re-checked this against the tree.

### The export shape the tests pin

`require("../../src/server/facility/Layout")` must return a table with six
**plain field functions, called with a dot**:

    Layout.generate(rng: Rng.Rng, tuning: MechanicsTuning.MechanicsTuning) -> Layout
    Layout.check(layout: Layout, tuning) -> { string }
    Layout.distance(layout: Layout, a: number, b: number) -> number
    Layout.neighbours(layout: Layout, id: number) -> { number }
    Layout.spawnRoom(layout: Layout) -> number
    Layout.spanningTree(rng: Rng.Rng, cells: { Cell }) -> { Door }

What the assertions destructure and therefore fix:

- **`Layout` value**: a table with **exactly** the keys `rooms`, `doors`,
  `spawnRoom` and no others (a memo in the value fails the plain-data test).
  `rooms[i]` has exactly the keys `id`, `column`, `row`; `doors[i]` exactly
  `a`, `b`. All numbers, 1-based.
- **`generate`**: `rooms[i].id == i`; rooms in strictly increasing row-major
  cell index; doors with `a < b`, sorted by `(a, b)`, no pair twice, each
  grid-adjacent; connected; degree ≤ 4; some pair ≥ 2 apart. Deep-equal on
  the same seed. It must call `rng:derive("cells")`, `rng:derive("tree")`,
  `rng:derive("loops")` **once each, in any order**, and must not call
  `nextInteger`, `nextNumber` or `shuffle` on the rng it was handed (a
  recording wrapper counts both). `layout.spawnRoom` must equal
  `Layout.spawnRoom(layout)` and the test's own argmin of eccentricity.
- **`check`**: returns `{}` on every generated layout and on the hand-built
  chain, square and cycle. For each violation fixture every returned string
  must start with `INV_layout:<token> ` (token, then a **space**) with token
  one of `room_count|cells|adjacency|connected` - any other shape is counted
  malformed and fails - and the expected token must be present. For the
  5-room fixture the token list must be exactly `{ "room_count" }`: one
  string, no other clause. The violation fixtures are (3 × 3 grid,
  `room_count` 6, ids as the 2 × 3 block `1 2 3 / 4 5 6`):
  - *cells*: room 6 at `(1, 2)` (room 4's cell), doors `1-2 1-4 1-6 2-3 4-5`
    - connected, every door grid-adjacent, so `cells` alone.
  - *adjacency*: the block, doors `1-2 1-4 1-5 2-3 3-6` - `1-5` is diagonal;
    connected without it, so `adjacency` alone.
  - *connected*: the block, doors `1-2 2-3 4-5 5-6` - two rows, no rung.
  - *room_count*: rooms 1..5 of the block, doors `1-2 1-4 2-3 4-5`.
  `check` is only ever handed six-room layouts and the 5-room control. But
  `distance`, `neighbours` and `spawnRoom` ARE handed a 5-room layout (the
  plus fixture), so they must work from `#layout.rooms`, not from
  `room_count`.
- **`distance`**: BFS edge count; `0` for `a == b`; symmetric; `math.huge`
  (compared with `==`) for an unreachable pair on a disconnected layout, which
  is handed to it without going through `check`. Must **raise** (observed via
  `pcall`) for `0`, `-1`, `7` and `2.5` on a six-room layout, in either
  argument position; must not raise for `1` and `6`. So the range check has to
  reject a non-integer, not only an out-of-range integer.
- **`neighbours`**: ascending list; a **fresh table each call** (the test
  appends to one result and expects the next call unchanged - a cached
  adjacency list returned by reference fails).
- **`spawnRoom`**: argmin eccentricity, ties to the lowest id. Fixtures:
  chain `1-2 2-3 3-6 4-5 5-6` -> 3 (tie 3/6); square `1-2 1-4 2-3 2-5 4-5 5-6`
  -> 2 (tie 2/5); cycle `1-2 1-4 2-3 3-6 4-5 5-6` -> 1 (six-way tie); plus
  (five rooms `(2,1) (1,2) (2,2) (3,2) (2,3)`, doors `1-3 2-3 3-4 3-5`) -> 3.
- **`spanningTree`**: door ids index `cells`; `a < b`; sorted by `(a, b)`;
  exactly `#cells - 1` doors; 1 cell -> `{}`; 2 adjacent cells -> `{ {a=1,b=2} }`.
  It is handed an rng whose `derive` **raises**, so it may use only
  `nextInteger`, `nextNumber` and `shuffle` on the rng it receives. It must not
  mutate `cells`. AC-3 tallies 150,000 draws, draw `i` from
  `Rng.fromSeed(1):derive("tree-" .. i)`, on the 2 × 3 block in row-major
  order; a draw that is not one of the 15 ladder trees (unsorted, short, a
  non-ladder edge) is counted as unknown and fails the test outright.
- **No mutation**: after `check`, every `distance`, every `neighbours` and
  `spawnRoom`, the layout deep-equals a snapshot taken before.

What the tests do **not** constrain, and so stays the implementer's:

- which cells any seed produces (forbidden by the Contract; no test looks);
- the free text after `INV_layout:<token> `, and the error message for a bad
  id;
- how cells are grown and how the walk is implemented, beyond the three
  derive labels and the rng-only `spanningTree`; the test does not check how
  many draws each sub-stream takes, nor their order;
- exported Luau **types** - the tests are untyped at the boundary (`any`), so
  `export type Cell/Room/Door/Layout` are for the typecheck gate, not for
  these tests;
- whether `check` would report more than one clause on a layout that breaks
  several - only the 5-room control is required to be single-clause;
- memoisation outside the `Layout` value.
