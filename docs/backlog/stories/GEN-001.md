## Context

Epic: `EPIC-04`. The facility is `room_count` rooms joined by doorways
(`mechanics.md` §1, G1–G2). Rooms are cells of a `layout_grid_columns` ×
`layout_grid_rows` grid. Doorways join only grid-adjacent rooms: a uniformly
random spanning tree first, then each other adjacent pair with probability
`layout_loop_door_chance`. Every player spawns in `spawn_room`, the room of least
eccentricity, with ties going to the lowest index. `INV_layout` states the
structural invariant (`tuning.md` §2).

The whole generator is built on distances: par, `INV_finale`'s
`paired_room_distance_min`, and the trace. This story builds the room graph and
the distance function everything else reads.

**Which required gate would fail if this story's artifact broke:** `unit`.

## Acceptance criteria

- **AC-1** — Given any seed in a sweep of at least 1,000, when
  `Layout.generate` runs, then `INV_layout` holds. There are exactly
  `room_count` rooms on distinct cells of the grid. Every doorway joins two
  grid-adjacent rooms. The doorway graph is connected. Every room has degree
  ≤ 4. Some pair of rooms is at least 2 edges apart.
  *Control:* `Layout.check` must report `INV_layout` for each of four hand-built
  violations, naming the broken clause: two rooms on one cell, a diagonal
  doorway, a disconnected pair, and 5 rooms.
- **AC-2** — Given the same seed and tuning, when `generate` runs twice, then
  the layouts are identical. Across the sweep, at least 20 distinct occupied-cell
  shapes appear.
  *Control:* a generator that always occupies the same six cells must fail the
  second clause.
- **AC-3** — Given the fixed 2 × 3 block of six cells, which has exactly 15
  spanning trees, when `Layout.spanningTree` draws 30,000 trees from derived
  streams, then each of the 15 trees appears with frequency within 1/15 ± 0.01
  (about 7 standard errors).
  *Control:* a tree built by breadth-first search from room 1 (one tree, always)
  must fail, scoring about 1.0 for one tree.
- **AC-4** — Given a hand-built layout with known shortest paths, including one
  with a loop and one that is a chain, when `Layout.distance(a, b)` is called
  for every pair, then it returns the number of doorway edges on a shortest path.
  The answer is 0 for `a = b` and symmetric.
- **AC-5** — Given hand-built layouts, when `Layout.spawnRoom` is called, then it
  returns the room of least eccentricity. When eccentricities tie, it returns
  the lowest room index. One fixture must have a tie.
- **AC-6** — Given a sweep, when extra doorways are counted, then the number of
  non-tree doorways divided by the number of non-tree adjacent pairs lies within
  `layout_loop_door_chance` ± 0.03.
  *Control:* a generator that never adds a loop door must fail, scoring 0.

## Contract

**Module.** `src/server/facility/Layout.luau`, pure.

    export type Room = { id: number, column: number, row: number }   -- 1-based cell
    export type Door = { a: number, b: number }                       -- room ids, a < b; doors sorted by (a, b) ascending
    export type Layout = { rooms: { Room }, doors: { Door }, spawnRoom: number }

    Layout.generate(rng: Rng.Rng, tuning: MechanicsTuning.MechanicsTuning) -> Layout
    Layout.check(layout: Layout, tuning) -> { string }       -- INV_layout violations; empty when valid
    Layout.distance(layout: Layout, a: number, b: number) -> number
    Layout.neighbours(layout: Layout, id: number) -> { number }  -- ascending
    Layout.spawnRoom(layout: Layout) -> number
    Layout.spanningTree(rng: Rng.Rng, cells: { {column: number, row: number} }) -> { Door }  -- exported for AC-3

- **Room ids** run `1..room_count` in row-major order of their cells (row first,
  then column). Every tie-break in the generator uses this id
  (`mechanics.md` §1).
- **Occupied cells** are grown from a uniformly drawn start cell, adding a
  uniformly drawn free cell that is grid-adjacent to the occupied set, until
  there are `room_count` cells. This is an implementation choice, pinned here
  for determinism. Only `INV_layout` and AC-2's variety are specified.
- **The spanning tree** is uniform over spanning trees of the occupied cells'
  adjacency graph. Wilson's algorithm (loop-erased random walks) satisfies this.
  Random edge order with union-find is not uniform in general. AC-3 is meant
  to tell the two apart, and `D-1` checks whether it can.
- **Randomness.** `generate` is handed an `Rng` the caller has already derived
  (`GEN-004` passes the attempt's `"layout"` sub-stream). It derives no labels
  of its own except `"cells"`, `"tree"` and `"loops"`, so that each draw is
  independent.
- **Distances** are breadth-first search over doors. Memoising is allowed, but
  never inside the `Layout` value, which stays plain data.

**Oracle partition.** AC-1, AC-4 and AC-5 are **mechanical** (and settled by
`tuning.md`'s rules). AC-3 and AC-6 are **oracle-free** statistics with
hand-written wrong generators as controls. The tolerances above are the Lead PO's
starting point, and RED may tighten them from a measured variance. AC-2 is
**mechanical**.

## Deferred verifications

**D-1. AC-3 tells a uniform tree from a merely random one.** Use
`scripts/mutate.sh` to replace Wilson's walk with random-order Kruskal ("shuffle
the edges, keep those that join two components"). Random Kruskal is not uniform
in general, but whether its bias on this 2 × 3 fixture exceeds AC-3's tolerance
is **not known at planning**. Record the measured frequencies. If Kruskal
passes, AC-3's fixture is too small to discriminate: say so, and the PO decides
between a larger fixture and waiving uniformity to "every spanning tree is
reachable". RED cannot run this. Owner: GATES.
